## Ticket P6-4a — markup split and authoring headroom (no parity rows)

Owns: `packages/markup/src/**` (shared compiler), `modules/markup-*/**` only where a hook moves, the `markup` web entry definition and new `markup-*` authoring entries you create, their tests. Do NOT edit `modules/text*/**`, `modules/fonts/**`, `packages/cli/src/font/**` or runtime (non-authoring) code.

Problem: the `markup` browser entry (AniML compiler for in-browser authoring) is 8,177 / 8,192 B, at the 8 KB module cap, and the authoring add-on gate is 15,226 / 16,384 B. P6 wave 2 will add markup for text effects and text input (~1 KB). Metric: `node tools/size.ts` lines `markup:` and `authoring add-on`. Targets: `markup` ≤ 7,400 B; authoring add-on ≤ 15,000 B **after** your change (total, not only `markup`). Guard: every AniML corpus file compiles byte-identically (`node tools/build-animl.ts --check` and the corpus test), `npm run test:scope -- markup conformance web` green, core+web unchanged.

Approach: profile which parts of `markup` are large (measure each source file's contribution, e.g. by bundling with/without it); move parts that only some documents need into optional `markup-*` entries loaded the way existing ones are (`markup-hooks`, `markup-text`, `markup-a11y`), and cut dead or duplicated code. Keep the public API and the `@anima-format/web/markup-hooks` import story for authors working; document any new entry an author must import in `docs/AUTHORING.md` and `spec/ANIML.md` §9. Log the decision ("decided, owner may revisit") in your report.
